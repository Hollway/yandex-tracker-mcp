# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Cursor, etc.) when working with code in this repository.

## Rules

Before naming a tool, writing a description, a CHANGELOG entry or a README section, read the rule that covers it - [`rules/README.md`](rules/README.md) indexes them, and each names the test that enforces it. This file covers the rest: architecture, the Tracker API's behaviour, and how to test.

## Project Overview

MCP Yandex Tracker is a Model Context Protocol (MCP) server that provides tools for interacting with Yandex Tracker API. It implements an `MCPServer` (mcp 2.x) with protocol-based architecture and optional Redis caching.

## Commands

```bash
task              # Run all checks (format, lint, type checking, tests) - REQUIRED before commits
task format       # Auto-format code
task check        # Run type and format checking
task test         # Run tests
uv sync           # Install dependencies
uv run yandex-tracker-mcp # Run the server
```

## Architecture

- **Protocols** (`mcp_tracker/tracker/proto/`): Define API contracts (`QueuesProtocol`, `IssueProtocol`, `GlobalDataProtocol`, `TemplatesProtocol`, `UsersProtocol`, `EntitiesProtocol`, `BoardsProtocol`, `ComponentsProtocol`, `WorkflowsProtocol`, `ReportsProtocol`, `DashboardsProtocol`), each exposed on `AppContext` as `queues` / `issues` / `fields` / `templates` / `users` / `entities` / `boards` / `components` / `workflows` / `reports` / `dashboards`
- **Client** (`mcp_tracker/tracker/custom/client.py`): Implements protocols, handles HTTP requests
- **Caching** (`mcp_tracker/tracker/caching/client.py`): Wraps protocols with Redis caching
- **MCP Server** (`mcp_tracker/mcp/server.py`): Server creation and configuration
- **MCP Tools** (`mcp_tracker/mcp/tools/`): Tool definitions organized by category
  - `_entity.py`: the tools projects, portfolios and goals share (links, ...), registered once per type from `project*.py` / `portfolio*.py` / `goal*.py` through `EntityKind`; their protocol methods take the entity type (`entity_get_links(entity_type, ...)`)
  - `_access.py`: Access control helpers (`check_issue_access`, `check_queue_access`, `check_workflow_access`); `_issue_access.py`: `check_issue`, the check of a tool acting on one issue, against the queue the issue is in now (see *Which queue an issue is in*)
  - `queue.py` / `queue_write.py`: Queue read-only / write tools; the administration ones (permissions, triggers, autoactions, macros, local field writes, queue create/delete/restore, issue type configuration) are in `register_queue_admin_tools` / `register_queue_admin_write_tools`, and `queue_get_workflows` in `register_queue_workflow_tools`
  - **Administration** (`settings.tracker_admin_enabled`, `TRACKER_ADMIN_ENABLED`, default off): the tools that configure Tracker rather than work its issues are registered only with it - the `register_*_admin_*` functions of `queue.py`, `queue_write.py`, `component.py`, `user.py` (`groups_get_all`) and `board_write.py` (boards and columns; sprints stay), and the whole of `component_write.py`, `user_write.py` and `template_write.py`. The workflow reads (`workflow.py`, `queue_get_workflows`) come with it or with the workflow writes, which need them. A new tool of that kind goes there; `ADMIN_READ_TOOL_NAMES` / `ADMIN_WRITE_TOOL_NAMES` in `test_server_creation.py` list them
  - `field.py`: Global field and metadata tools (read-only), with `fields_find` / `field_get_values` (their logic in `_field_lookup.py`)
  - `template.py` / `template_write.py`: Issue and comment template read-only / write tools; `issue_create` (in `issue_write.py`) takes an issue template as `template_id`
  - `application.py`: External application tools (read-only)
  - `board.py`: Board, column and sprint tools (read-only), including `board_get_sprint_issues`, which reuses `find_issues` from `issue_read.py`; `board_write.py`: board, column and sprint write tools, not covered by the queue restrictions (a board belongs to no queue)
  - `component.py` / `component_write.py`: Queue component read-only / write tools (`queue_get_components` itself lives with the queue tools)
  - `issue_read.py` / `issue_write.py`: Issue read-only / write tools
  - `user.py`: User tools (read-only); `user_write.py`: absence create / delete, not covered by the queue restrictions
  - `worklog.py`: Worklog search across issues (read-only)
  - `report.py` / `report_write.py`: Issue report read-only / write tools; `report_create` is refused under `TRACKER_LIMIT_QUEUES`
  - `dashboard.py` / `dashboard_write.py`: Dashboard read-only / write tools, not covered by the queue restrictions except `dashboard_add_cycle_time_widget`, refused under `TRACKER_LIMIT_QUEUES`
  - `workflow.py` / `workflow_write.py`: Workflow and transition screen read-only / write tools (`queue_get_workflows` itself lives with the queue tools); `workflow_write.py` is only registered when writes are on and `settings.tracker_workflows_write_enabled=True`
  - `catalog_write.py`: Status, resolution, issue type and priority write tools (`status_*`, `resolution_*`, `issue_type_*`, `priority_*`), registered under the same flag as `workflow_write.py`; the reads are the legacy `get_statuses` etc. in `field.py`
  - `filter.py` / `filter_write.py`: Saved issue filter read-only / write tools (`filter_*`); a filter belongs to no queue, so only `TRACKER_READ_ONLY` applies
  - `field_write.py`: Issue field and field category write tools (`field_create`, `field_update`, `field_create_category`, `field_update_category`), same flag and same queue-restriction rule as `catalog_write.py`; the reads (`field_get`, `fields_get_categories`) are in `field.py`
  - `__init__.py`: Exports `register_all_tools()` which orchestrates tool registration
  - `*_write.py` modules are only registered when `settings.tracker_read_only=False`
  - project/portfolio/goal modules are only registered when `settings.tracker_entities_enabled=True`
  - `issue_add_attachment` (`register_issue_file_upload_tools` in `issue_write.py`) and `attachment_create` (`attachment_write.py`) are only registered when writes are on and `settings.tracker_file_upload_enabled=True`; both read the file through `_files.read_upload_file`
  - `issue_download_attachment` (`register_issue_attachment_download_tools` in `issue_read.py`) is only registered when `settings.tracker_attachment_download_enabled=True` - in read-only mode too, since it changes nothing in Tracker
- **Settings** (`mcp_tracker/settings.py`): Pydantic settings from environment variables
- All protocol methods accept optional `auth: YandexAuth | None` parameter for OAuth support.
- All Pydantic models for Yandex Tracker entities inherit from `BaseTrackerEntity`.

### Talking to the Tracker API

- **Reference fields** (`type`, `priority`, `parent`, `sprint`, `followers`, `components`, `project`) use the shared models in `mcp_tracker/tracker/proto/types/inputs.py` (`Issue*Ref`), serialized by `_ref_body()` in the client. How Tracker resolves a bare value is per field, so check before widening a parameter: `type` / `priority` accept an id or a key and resolve a numeric string as an id (verified against the API), `followers` accept a uid or a login the same way, and a 422 from these means the referenced entity does not exist. `components` are the exception - a bare string there is a *name*, which makes a numeric-looking name ambiguous (this is what `components: ["694"]` answered 422 for), hence `IssueComponentRef` requiring exactly one of `id` / `name`. Create and update must accept and send the same value the same way - the API takes a bare key or id on both, so a parameter widened on one has to be widened on the other, or an agent that created an issue with a scalar hits a schema error when it updates the same way.
- **Every request goes through `self._request()`** - or `self._read()`, which is `_request` plus reading the body and is what a method wanting nothing but the body uses. Nothing calls `self._session` directly: the funnel is what builds the auth headers, translates a `TimeoutError` into `TrackerAPITimeout` (`str(TimeoutError())` is the empty string, so an untranslated timeout reaches an agent as a message with nothing in it), translates aiohttp's `ClientError` (DNS, a refused connection, a dropped body) into `TrackerAPIConnectionError` and puts every response through `_raise_for_status`, so Tracker's own `errorMessages` / `errors` end up in the raised `TrackerAPIError` instead of a bare "Unprocessable Entity". The funnel exists because these were sixty copies of the same lines and the copies drifted; a method added beside it rather than through it starts that again.
- **Errors**: statuses with an actionable meaning are passed to the funnel as `not_found=` / `conflict=`, ready to raise: 404 → `IssueNotFound` on issue-scoped paths, `QueueNotFound` on queue-scoped ones (`v3/queues/{queue}/...`), `BoardNotFound` on board-scoped ones, `ComponentNotFound` on `v3/components/{id}` and the similar error on other paths; `conflict=` covers 409 *and* 412 - a stale `version` answers 409 on an issue update (`IssueVersionConflict`) but 412 on a component update (`ComponentVersionConflict`), and both are the same precondition failure. A dedicated error applies to *every* method scoped to that entity, not just to newly added ones. `allow_statuses=` is the way out for a status that is an answer rather than a failure - `user_get` reads a 404 as `None`; an allowed status skips `not_found` / `conflict` / `_raise_for_status` alike and reaches the caller as an ordinary response. An exception meant to reach the agent subclasses `ToolError` (`TrackerError` and `YandexTrackerError` do, so everything under them does too): mcp 2.x forwards a `ToolError`'s text in the tool result and hides any other exception behind a bare `Error executing tool <name>`. That is why a client method never raises a bare `ValueError` for something the caller can act on - `issue_close` with no transition to a `done` status raises `NoDoneTransition` (naming the transitions there are), a request that cannot be authenticated or attributed to one organization raises `TrackerAuthConfigError`. What deliberately stays a crash: a response body that fails to parse into its model and a Redis error under `TOOLS_CACHE_ENABLED` - both are the server's problem, not the caller's, and the traceback belongs in the server log.
- **429 Too Many Requests** (seen on the live API 2026-10-16 from four parallel tool calls, and from single calls in a row): the funnel sends the request again - writes too, since Tracker refuses it before running it - after `Retry-After` (seconds or an HTTP date) or 1, 2 and 4 seconds, then raises `TrackerRateLimited` (a `TrackerAPIError` with status 429). A `Retry-After` over 10 seconds is raised at once rather than sat out. A multipart body (`data=`, the attachment uploads) is not retried: aiohttp's `FormData` is not safe to send twice.
- **Field names on the wire**: a model may use a snake_case Python name, but it must accept *and emit* Tracker's own name - set `serialization_alias` next to every `validation_alias` (`story_points` reads and writes `storyPoints`). Responses are what callers feed back into `fields`, so the two spellings have to match; `tests/tracker/proto/test_model_aliases.py` fails if a new field forgets this.
- **`fields` maps**: `issue_create` / `issue_update` take the free-form map as an explicit `fields` parameter, never as `**kwargs` - a key naming a dedicated parameter used to raise `TypeError: got multiple values`. The client merges it into the body last, so an entry overrides the dedicated parameter and an explicit `null` clears the field (a dedicated parameter left as `None` is simply not sent).
- **Reference inputs**: every `Issue*Ref` validates that it carries something to resolve (`IssueComponentRef` wants exactly one of `id` / `name`, the others at least one of `id` / `key`); Tracker answers an empty object with an unhelpful 400/422, and when both `id` and `key` are set it resolves by `id`.
- **Issue `version`**: it is bumped by every change, including queue triggers and automation that fire right after creation, so the version returned by `issue_create` is routinely stale. Tools that accept `version` must say so and point at `issue_get` for a fresh read.
- **Issue checklists** (`v3/issues/{id}/checklistItems`) behave unlike the entity ones: `POST` takes exactly one item per request, so `issue_add_checklist_items` loops over the batch (a failure past the first item raises `ChecklistBatchPartiallyAdded`, which reports how many landed - nothing is rolled back), and `PATCH .../{itemId}` takes a JSON **object** of just the fields being changed. Both halves of that contradict the documentation, and both were verified against the live API on 2026-08-27: the docs show an array body (`[{...}]`, which answers 400) and call `text` required (it is not - a `PATCH` with only `checked` or only `assignee` answers 200 and leaves the existing text intact). Do not "fix" either back to what the docs say. An empty body is also a 200 no-op, so an update with nothing to change is refused locally with `ChecklistItemEmptyUpdate`. `assignee` and `deadline` are cleared by an empty object (`{}`), which is what `clear_assignee` / `clear_deadline` send - verified on the live API on 2026-08-31, along with the three spellings that do not work: `null` answers 200 and silently keeps the value, `""` and `0` answer 422. Setting and clearing the same field in one call is refused with `FieldClearConflict` rather than letting one of the two win silently. A 404 from the item-scoped paths (`PATCH`/`DELETE .../checklistItems/{itemId}`) means an unknown issue *or* an unknown item, so it raises `ChecklistItemNotFound(..., ambiguous=True)`, whose message names both - `IssueNotFound` there would assert the one cause Tracker does not distinguish, and the same bad id would report differently depending on whether `text` was passed. `issue_add_checklist_items` with an empty batch returns `issue_get_checklist` rather than `[]` - the method's contract is "the checklist after adding", which an empty list misstates for an issue that already has items. Every one of these endpoints answers with the whole issue object, from which only `checklistItems` is parsed (the key is absent once the checklist is empty). `DELETE v3/issues/{id}/checklistItems` (the collection path, `issue_delete_checklist`) removes every item and answers 200 with the issue, also for an empty checklist, bumping the version either way (verified 2026-10-26). There is no per-item reconcile step here - that quirk belongs to the entities' bulk `PATCH`, see `_reconcile_checklist_update`.
- **Queue components** (verified against the live API on 2026-09-06): only `GET v3/components` (organization-wide, paginated, ignores a `queue=` filter), `POST v3/components` and `PATCH v3/components/{id}` are documented. The server uses the undocumented queue-scoped `GET v3/queues/{queue}/components` (the full objects of one queue, no pagination headers) and `GET v3/components/{id}` / `DELETE v3/components/{id}` instead - the org-wide listing pages through every component the organization has (1002 of them here - 21 requests to find a queue's 13). `expand=components` on `GET v3/queues/{queue}` returns references only (`id` as a string, `display`), no `version`, `lead` or `assignAuto`. `PATCH` **requires** `version` as a query parameter: without it the API answers **428**, and a stale one answers **412** (not 409) - the *Errors* bullet above says how `conflict=` covers both. An empty `PATCH` body answers 200 and changes nothing (the version does not move), so `component_update` refuses it locally with `ComponentEmptyUpdate`; re-sending the value a field already has answers 200 without bumping `version` either. `lead` is sent as a login or a uid (a login like `"i.ivanov"`, a uid as a number or as a string, and `{"id": "<uid>"}` all answer 200 with the same user object; an unknown login answers 422) and comes back as a user object. **`lead: {}` clears the lead** (200, no `lead` in the response, version bumped), which is what `clear_lead` sends; the two spellings that do not work are the checklist ones again: `null` answers 200 and silently keeps the current lead, `""` answers 422. `lead` and `clear_lead` together are refused locally with `FieldClearConflict`. `description: ""` clears the description (`null` changes nothing); `name: ""` answers 422. `DELETE` answers 204 with no body and takes no `version`; deleting again, or reading afterwards, answers 404. `description` and `lead` are absent from a response when unset. Component reads are **not cached** (`component_get`, `queues_get_components` delegate without `@cached`): the `component_update` / `component_delete` tools read through the protocol to get the `version` the API demands (428 without one) and to learn the queue, and there is no omit-version escape as there is for issues, so a cached read would feed the `PATCH` a stale version for the rest of the TTL. The `component_update` / `component_delete` tools take a bare id, so under `TRACKER_LIMIT_QUEUES` / `TRACKER_READ_ONLY_QUEUES` they read the component once to learn its queue (`queue_checks_needed` in `_access.py` says when); `component_update` also reads it when the caller gave no `version`. One GET at most, then the write. A component in a queue outside `TRACKER_LIMIT_QUEUES` is reported as `ComponentNotFound` by `check_component_access` - the caller knows it by id alone, and a queue the allow-list hides must not be named back at them.
- **Attachments** (`POST v3/issues/{id}/attachments/`, trailing slash, 201): a multipart body whose part is named `file`; the stored name goes both as the documented `?filename=` query parameter and as the part's filename (aiohttp percent-encodes a non-ASCII part filename). The upload runs under `TRACKER_ATTACHMENT_TIMEOUT`, not the per-request budget. An image shows inline in an issue description only when referenced as `![name](/ajax/v2/attachments/<id>?inline=true)` - a bare file name or the `api.tracker.yandex.net` URL renders as a broken image (seen in production use). Attaching to a comment goes through a temporary attachment: `attachment_create` uploads it the same way to `POST v3/attachments/` (no issue in the path), and its `id` goes into `attachmentIds` of the new comment (`attachment_ids` of `issue_add_comment`); the comment then lists its files in `attachments`. The download URL is `GET v3/issues/{id}/attachments/{attachmentId}/{name}` - the `content` field of an attachment, with the name percent-encoded; `issue_download_attachment` first reads the attachment's own metadata, `GET v3/issues/{id}/attachments/{attachmentId}`, for that name and for the size, which is checked against `TRACKER_MAX_ATTACHMENT_BYTES` before a byte is fetched; a 404 there means an unknown attachment *or* an unknown issue (`AttachmentNotFound` names both). The body is streamed to `<file>.part` and renamed when complete, so a file under its final name is always whole and a repeated download reuses it. `thumbnail=True` fetches `GET v3/issues/{id}/thumbnails/{attachmentId}` instead (verified 2026-10-26): a 140x140 PNG for a PNG and a JPEG alike (saved as `<id>-thumbnail-<stem>.png`, not held to the size limit), and 404 "Миниатюра не существует." for anything but an image, raised as `AttachmentThumbnailNotFound` - the attachment was read just before, so it exists. The attachment metadata of an image carries a `thumbnail` URL and `metadata.size` ("400x400").
- **AI tools access** (verified on the live API 2026-10-15): `GET v3/queues/{key}` reports the queue setting 'Доступ для AI инструментов' as `aiAccessLevel` (`"full"` allows) and `noMcp`; the API itself does not enforce it, Tracker's own MCP server does. `tools/_ai_access.py` does the same: a queue with `noMcp: true` or an `aiAccessLevel` other than `"full"` gets its issues back from `issues_find` as `{key, restricted: true}`, the single-issue reads raise `AiAccessRestricted`, `worklogs_find` drops comments, writes are untouched. The answer per queue is kept for ten minutes in `AppContext.ai_access`; a queue the token cannot read (404, 403) counts as allowed, while any other failure reading the setting (a 429, a timeout) is raised and not remembered - taken for "allowed", it opened the queue for the whole TTL. `issues_find` adds `key` to a projection so that each row's queue is known, and a listing reads the settings of its distinct queues at once (`ai_restricted_queues`). `issue_get_links` / `issue_get_remote_links` are checked too: a link carries the linked issue's summary. `TRACKER_AI_ACCESS_IGNORED_QUEUES` opts queues out.
- **Which queue an issue is in**: `queue_of_key()` in `_access.py` is the one place that reads it from an id - `QUEUE-123` names `QUEUE`, anything else (Tracker also takes an issue's internal id, `6ad1d166dc7d9f59dec67d79`) names none. Tracker also serves a moved issue under its old key (verified 2026-10-27: after `issues_bulk_move` `MCPTMV-1` answers as `MCPTMW-2`, the old key in `aliases`), so a key can name the queue the issue has left. A tool acting on one issue therefore calls `check_issue` (`_issue_access.py`): it checks the key as passed first, so a queue out of reach is refused without a request, and then reads the issue for the key it comes back under - but only when that can change the answer: when the queue restrictions apply to the call (`queue_checks_needed`), or, for a read carrying the issue's content, when some queue forbids AI tools. That last one is `ai_forbidden_anywhere` in `_ai_access.py`: one `queues_list` pass every ten minutes (`AppContext.ai_forbidden_anywhere`), which fills the per-queue answers on the way, since the listing reports `aiAccessLevel` / `noMcp` too. On a server with neither an issue costs no extra request. An internal id goes through the same read, so it is accepted under a restriction. `issue_get` and `field_get_values` read the issue anyway and check the key it comes back under (`check_fetched_issue_access`, `check_fetched_issue_ai_access`; an issue without a key is refused under `TRACKER_LIMIT_QUEUES`). The bulk tools still go by the keys passed (`check_issue_access`, which refuses an internal id under a restriction): up to 10 000 issues are not read one by one, so the old key of a moved issue is checked against its old queue there.
- **Remote links** (verified on the live API 2026-10-16): `POST v3/issues/{id}/remotelinks` with `origin: "com.gitlab"` and an arbitrary key answers 200 - Tracker does not check that the object exists - and `DELETE .../remotelinks/{id}` removes it. `origin: "ru.yandex.wiki"` answers **403 "Не указан заголовок 'X-Iam-Token'"**: Tracker reads the wiki page on the user's behalf and wants an IAM token in that header, which this server never sends (an OAuth token cannot be one). The tool description says so; sending `X-Iam-Token` under IAM auth is untried.
- **Triggers, autoactions, macros** (from the API reference, not tried on the live API unless dated): the reference documents trigger get / create / `PATCH ...?version=` (409 *and* 412 for a stale version → `TriggerVersionConflict`) and the webhook run log (`GET .../triggers/{id}/webhooks/log`, 10 entries unless `limit`, at most 100). It has no trigger delete, but the undocumented `DELETE v3/queues/{q}/triggers/{id}` works (verified 2026-10-26 on a temporary queue: 204 without `version`, then 404 "Триггер не существует." to a read or a second delete) - `queue_delete_trigger`; `active: false` still switches one off without deleting it. For autoactions only get, create (`filter` or `query` required) and the launch logs (`.../logs`, `.../logs/{runId}`) are documented - no update or delete; the listing `GET v3/queues/{q}/autoactions` is undocumented and answered `200 []` on the live API (2026-10-23). Macros have get / list / create / `PATCH` / `DELETE` (204) and no `version`; the reference calls `name` required on `PATCH` too, so `queue_update_macro` reads the macro for its name when none is given, and `body: {"unset": 1}` clears the comment. A 404 on an item path means an unknown queue *or* item (`TriggerNotFound` / `AutoactionNotFound` / `MacroNotFound` name both). Actions and conditions stay free-form dicts; webhook credentials and headers are dropped from responses (`_drop_secrets`), and in a queue that forbids AI tools the log tools drop the webhook request body and issue summaries. Trigger / macro single reads, logs and `queue_get_fresh` are not cached; the listings and `queue_get_autoaction` are.
- **Queue administration** - `POST v3/queues` (create, 201), `DELETE v3/queues/{q}` (204) and `POST v3/queues/{q}/_restore` (administrators only) are documented. Verified on the live API 2026-10-23 on a temporary queue: `v3/queues/{q}/issuetypes` is GET-only (POST answers 405, `.../issuetypes/{type}` has no route), and the undocumented `PATCH v3/queues/{key}` with `{"issueTypesConfig": [{"issueType", "workflow", "resolutions"}, ...]}` answers 200 and **replaces the whole list** - a type is added, re-pointed to another workflow or removed by leaving it out. Leaving out the default type answers 422 with an empty `errorMessages` unless the same body moves `defaultType` to a type that stays (`queue_remove_issue_type` refuses that locally); a `resolutions` list missing one the workflow's transitions set answers 422 with a readable text, passed through. The `version` query parameter is ignored there (a stale one is accepted), and the same `PATCH` renames the queue with `{"name": ...}`. The current list comes from `GET v3/queues/{key}?expand=issueTypesConfig` (`issueType` / `workflow` / `resolutions` as references), read uncached through `queue_get_fresh` because the write sends it all back. What happens to existing issues in a status the new workflow lacks is untried through the API (the UI asks for a status mapping). A `DELETE` right after the queue changed answered **412** "Очередь: не удалось сохранить изменения, попробуйте ещё раз" (the sprint quirk again) and passed when sent again, so `queue_delete` retries a 412 after 2, 5 and 10 seconds; a deleted queue answers 403 to a read. Live-checked through the tools on 2026-10-23: create, issue-type re-pointing and removal, delete, restore, and the macro create/update/clear/delete cycle in a real queue.
- **Bulk changes** (`POST v3/bulkchange/_update|_transition|_move`, 201) are queued and run in the background; `GET v3/bulkchange/{id}` gives the state (`CREATED`, `RUNNING`, `RUNNING_FAILING`, final `COMPLETE` / `FAILED`) and `GET v3/bulkchange/{id}/issues` the issues it failed on with Tracker's `errors`. `notify` is a query parameter, false by default; `moveAllFields` / `initialStatus` go in the move body. The tools (`register_issue_bulk_tools`, `TRACKER_BULK_ENABLED`, writable server) check every issue with `check_issue_access(write=True)` and ask for a confirmation by elicitation where the client can.
- **Sprints** (`v3/sprints`): `PATCH`, `_start` and `_archive` take the sprint's version as `If-Match: "<version>"` (passed through `_request(extra_headers=...)`); the tools read the sprint first when the caller gives no `version`, so sprint reads are not cached. Both 409 and 412 map to `SprintVersionConflict`. The board id goes in the create body as a string. Verified on the live API 2026-10-16 (board 162): only a scrum board has sprints - any other answers 400 "У доски этого типа не может быть спринтов". **Right after a sprint changes, Tracker now and then refuses a write made with its current version** - 412 "Спринт: не удалось сохранить изменения, попробуйте ещё раз", the same status and text a stale version gets, whether the version goes as `If-Match` or as `?version=`; the same request passes 15 seconds to a minute later. So when the caller gave no `version`, `_write_current` in `board_write.py` re-reads it and writes again after 2, 5 and 10 seconds; a caller's own version still raises. The API takes dates only: `startDate` / `endDate` become midnight UTC (`startDateTime` / `endDateTime`, which answer 400 "Incorrect data format" to every spelling tried), while the UI sets local midnight and the end of the last day. `_start` moves `startDate` / `startDateTime` to now. `DELETE` works on a running or archived sprint.
- **Boards and columns** (verified on the live API 2026-10-26 on temporary boards 163 and 166, both deleted): create is `POST v3/liveBoards` (201) - the documented-as-deprecated `POST v3/boards` ignores the body. `PATCH v3/boards/{id}` and every column write (`POST v3/boards/{id}/columns`, `PATCH`/`DELETE .../columns/{colId}`) **take no version at all** although the reference demands `If-Match` for the column writes; given, it is the **board's** version as `If-Match: "N"` (the quotes are required, a bare number answers 400) or `?version=N`, and a stale one answers **412** "Доска: не удалось сохранить изменения" → `BoardVersionConflict`. A column has no version of its own: each column write bumps the board's, and the `ETag` of a write's answer carries the version *before* it. An empty board `PATCH` is a 200 no-op, an empty column `PATCH` a 200 that still bumps the version - both refused locally (`BoardEmptyUpdate`, `BoardColumnEmptyUpdate`). `columns` in a board `PATCH` replaces every column, under new ids. The board's auto-filter (`autoFilters.addFilter.liveFilter.fieldValues: {field: [{"fixed": value}]}`) is accepted on create only: `PATCH` answers 400 to `autoFilters`, `autoFilterSettings` and `addFilter` alike, and `owner` cannot be changed either (400). `backlogAvailable` / `sprintsAvailable` switch sprints (a board without them answers `.../sprints` with 400) and are not in the board read. A column's `limit` (in the column read, missing from the reference) can be set and changed but not removed: `null` and `""` change nothing, `0` and `{}` answer 422/400. Tracker does not stop one status sitting in two columns. A 404 on the column paths carries Tracker's words for what is missing ("Колонка не существует." / "Доска не существует."), so no `not_found=` is passed there. `DELETE v3/boards/{id}` (204) deletes the board's sprints with it.
- **The issues of a sprint**: the YQL `Sprint: <id>` matches by id (the name works too, but can match two sprints) and is what `board_get_sprint_issues` sends through the same search as `issues_find`; an unknown id matches nothing rather than failing, so an empty first page reads the sprint for a `SprintNotFound`. The undocumented `GET v3/sprints/{id}/issues` gives the same set but unpaged, ignoring `perPage` and `fields`. The burndown snapshot of the issues planned at the sprint's start, which Tracker's own MCP server reads, is not in the public API: `v2`/`v3` `sprints/{id}/burndown` and a dozen other spellings answer 404 (2026-10-26).
- **Workflows** (verified on the live API 2026-10-23, test workflow W9 in queue ORG): documented are `GET`/`POST v3/workflows`, `GET`/`PATCH`/`DELETE v3/workflows/{id}`, `GET v3/queues/{queue}/workflows` (workflow id → issue types) and `PATCH v3/workflows/{id}/steps/{status}/actions/{actionId}`; undocumented but working are `POST .../steps/{status}/actions` (adds one transition), `GET v3/screens` and `GET v3/screens/{id}`. There is **no `DELETE` for one transition** (that path takes only `PATCH`, 405 otherwise): removing a transition, adding or removing a status means `PATCH`ing the whole `steps`, which replaces every step. Every write needs `?version=N` (400 without it); a stale one answers **412** "Воркфлоу: не удалось сохранить изменения, попробуйте ещё раз." → `WorkflowVersionConflict`. **Reads and writes take different shapes**: a read gives names as strings in the `Accept-Language` language and statuses, screens, resolutions and fields as reference objects (`statusType` in lower case, `"done"`), while a write wants `name` / `description` as `{"ru": ..., "en": ...}` (a string answers 400, `ru` alone 422), `target` and `status` by key, and a reference inside `postFunctions` by key or id. **A `PATCH` of one action replaces it whole**: `name` and `target` are required, and whatever is omitted (screen, `postFunctions`, `description`, `actionCoords`) is removed - so an update reads the action, merges the caller's changes and sends all of it. **Screens go inline and are re-created**: a write cannot refer to an existing screen by id (every spelling answers 400), only send `{"title": {ru, en}, "elements": [{"field", "required"}]}`, and Tracker creates a new screen with a new id each time and deletes the one it replaces (a `GET` of the old id answers 404 "Экран перехода не существует"). Tracker's own workflow editor saves the same way - an edit there re-creates every screen of the workflow too. **Transition conditions** (`conditions`, a list that must all hold) read and write as `{type, ...}` objects with references by key or id: `UserInFieldCondition {field}`, `UserIsQueueLeadCondition`, `UserInListCondition {users: [uid]}` (a login answers 422 "не существуют"), `UserInGroupCondition {group: id}`, `ToPreviousStatusOnlyCondition`, and `OrCondition` / `AndCondition {conditions: [...]}` for nesting. One type differs between the two: the linked-queue condition reads back as `HasLinksConditionProto` and must be written as `HasLinksCondition {queues: [key]}` (the read name answers 400 "conditions: Incorrect data format"), which `_condition_drafts` maps - without it any rewrite of a workflow carrying that condition fails. Verified 2026-10-23 on W9 with conditions set up in the UI: they survive a one-transition update and a whole-workflow rewrite. `DELETE v3/screens/{id}` answers 405; `POST v3/screens` creates a screen attached to nothing, which no write can then use. `workflow_get_draft` reads the workflow in `ru` and in `en` and reads every screen it uses; written back unchanged through `workflow_update(steps=...)` it leaves the workflow identical - names in both languages, descriptions, `postFunctions`, coordinates, `statusType`, screen fields and titles - except the new screen ids (verified). A new status needs at least one transition into it from a reachable step, or the write answers 422 "Статус(ы) "..." недостижим(ы) из начального статуса", which reaches the caller through the funnel. A 404 on the action-scoped paths carries Tracker's own text ("Переход не существует." / "Статус не существует.") and is passed through as `TrackerAPIError(404)` rather than claiming the workflow is unknown. Workflow and screen reads are **not cached** (`CachingWorkflowsProtocol` delegates): the write tools read the current `version` and draft before writing, and a cached read would feed them a stale one. `check_workflow_access` goes by the queue the workflow is bound to; a shared workflow (no queue - the 16 `*PresetWorkflow` ones) can be read but not written under a queue restriction.
- **Statuses, resolutions, issue types, priorities** (the organization's catalogue, `GlobalDataProtocol`; from the API reference, not yet checked against the live API): `POST v3/{statuses,resolutions,issuetypes,priorities}` and `PATCH .../{id or key}?version=N` (organization-administrator rights). A write takes `name` as `{"ru", "en"}`; `key` is set on create only. The reference documents a stale `version` as 409 for some and 412 for statuses - both raise `CatalogVersionConflict` through `conflict=`. It also shows some `PATCH` bodies as a one-element array and some answers (status and issue type) as one, which is taken for noise: an object is sent, and `_one_catalog_object` accepts an object or a one-element array. When the caller gives no `version`, the tool reads the object first through the undocumented single read `GET .../{id or key}` (its `self` URL), which is not cached. **There is no `DELETE` for any of them** - a mistaken one can only be renamed. An update is refused under `TRACKER_LIMIT_QUEUES` / `TRACKER_READ_ONLY_QUEUES` (it shows in every queue); a create is not.
- **Issue fields and field categories** (verified on the live API 2026-10-26, test field `mcpTestField` in category `MCP test`, both left in place): `v3/fields` and `v3/fields/categories` go through the catalogue helpers (`_FIELDS`, `_FIELD_CATEGORIES`). A field create answers **200** (the reference says 201), a category create 201. An update needs `?version=` (**428** without it, **412** "Поле: не удалось сохранить изменения" for a stale one) and takes any subset of the fields; an empty body answers 200 and bumps the version, so it is refused locally. `optionsProvider: null` changes nothing; a new `optionsProvider` replaces the whole list, and its `type` must match the field (`FixedUserListOptionsProvider` for a user field), which is why `field_update` reads the field when `options` is given. `name` as a bare string answers 422; `{"ru": ...}` alone is accepted. **There is no DELETE** for either (405 "DELETE is not allowed ([PATCH, GET])"). A category answer carries only `id`, `name`, `self`, `version`.
- **Finding a field, and the query language** (verified on the live API 2026-10-26): `GET v3/fields` and `.../localFields` name a field in the `Accept-Language` language (none: the organization's), so `fields_find` reads both `ru` and `en` (`language=` on `get_global_fields` / `queues_get_local_fields`, cached per language). **The query language names a field by its name, not its id**: `storyPoints: notEmpty()` answers 422 "Фильтр storypoints не существует", `"Story Points"` and the Russian name work; a local field is `SAP."System ID"` (the queue key is case-insensitive there, the field key is refused), and a `hidden` field or one without `queryProvider` cannot be searched by at all - hence `ql_name` from the English name, absent for those. `GET v3/queues/sap/localFields` answers 404 for a lower-case key, so the tools upper-case it. What a value is comes from `optionsProvider` (`FixedListOptionsProvider` carries the list) and `schema.type` / `schema.items`. Resolutions per issue type come from `expand=issueTypesConfig`, whose entries are references (`display`, not `name`).
- **Local fields and queue tags** (verified 2026-10-26 on the temporary queue MCPTMR): `v3/queues/{q}/localFields/{key}` is addressed by the field's **key**; the `id` that comes back is `<hash>--<key>` (the full id as a path answers 404), and that `id` is what an issue write takes - `{"locTest": ...}` on `POST v3/issues` answers 400 "Field [locTest] was not found". A create answers 200; an update needs no `version` and ignores a stale one; there is no DELETE (405). `POST v3/queues/{q}/tags/_remove` with `{"tag"}` answers 204, also for an unknown tag; a tag still on an issue answers 422 "Тег ещё используется", and kept answering so for 10-15 minutes after the tag was taken off the issue (then 204).
- **Queue permissions** (verified 2026-10-26 on the temporary queue MCPTMS): `GET v3/queues/{q}/permissions` is undocumented but answers the whole object (`create` / `read` / `write` / `grant` / `deny`, each with `users`, `groups`, `roles`, plus `version`). `PATCH` takes, per permission and per kind, either a list (replaces it) or `{"add": [...], "remove": [...]}`; it ignores `version` (a stale one is accepted), answers an empty body 200 without a change, and **does take a role in `deny`** although the reference says roles cannot be denied. An unknown user or group answers 422 ("пользователи [...] не существуют", "группы [...] не существуют"). `.../permissions/users/{login}` and `.../groups/{id}` give one subject's permissions with what each comes through (upper-case keys). Components have the same reads under `v3/components/{id}/permissions...`; their `PATCH` (`component_update_permissions`, verified 2026-10-27 on a temporary component) takes the same bodies but wants the **permissions'** `version` - not the component's - as `?version=` (**428** without it, **412** for a stale one → `ComponentPermissionsVersionConflict`), has no `deny`, and answers an empty body 200 without a change. A component nobody restricted answers `GET .../permissions` with `{version}` alone; the first change restricts it, and Tracker adds the robot and the role `queue-lead` to `create`, `write` and `grant` by itself. Group ids come from `GET v3/groups` (paginated). `queue_update_permissions` asks the user to confirm by elicitation, the way the bulk tools do.
- **Saved filters, comment reactions, suggest, queue forms** (verified on the live API 2026-10-26, temporary queue MCPTMT and test issue ORG-14): `POST v3/filters` answers **200** (the reference says 201); `name` is required (422 "Отсутствует название фильтра"), and `query` together with `filter` answers **409** "Поля 'filter' и 'query' указаны одновременно", refused locally with `FilterConditionsConflict`. `PATCH v3/filters/{id}` takes any subset and no `version`; new `query` drops `filter` and the other way round; an empty body answers 200 and changes nothing (`FilterEmptyUpdate`). `sorts` (`[{field, isAscending}]`) and `fields` (the UI columns) are written as field keys but read back as field references, the key resolved to the field id (`created` → `createdAt`), hence the separate `FilterSort` input and `FilterSortRead`. `DELETE` answers 204 on **v3** as well as on the documented v2. There is **no listing** of filters: `GET v3/filters` answers 405 (POST only) and `v3/filters/<anything>` is taken for an id; ids are small organization-wide integers, other users' filters are readable (one answered 500). The READ permission of a new filter is the group of all employees. `filterId` in the body of `POST v3/issues/_search` / `_count` searches by a saved filter (unknown id → 422 "Фильтр не существует."): with `query` or `filter` it gives the **intersection**, while `keys` or `queue` override it - `issues_find` sends only `query` and `filterId`. Comment reactions: `POST .../comments/{id or longId}/reactions/{REACTION}` and the undocumented `DELETE` of the same path both answer 200 with the comment, `reactionsCount` (lower-case names) and `ownReactions`; the name is case-insensitive, an unknown one answers 400, a repeated add or a delete of an absent reaction 422 with Tracker's text, and each change bumps the comment's `version`. `GET v3/issues/_suggest?input=` returns at most 20 issues (`display` = summary; `full=true&fields=` gives real fields) and **ignores `queue`** (it validates it - a number answers 400 - but returns the same rows), so `issues_suggest` filters by key itself. `GET v3/queues/{q}/forms` answers `{queue, forms, version, showDefaultCreationForm}`; no queue here had a form, and `POST .../forms` needs a real Yandex Forms id or path (422 "неизвестный экземпляр формы"), so a form's own fields are the official MCP's (`id`, `name`, `description`, `path`) and the rest passes through. Filter reads are not cached (a filter is read back right after an update); suggest and forms are.
- **Entity links** (verified on the live API 2026-10-26 on temporary projects): `GET v3/entities/{type}/{id}/links` without `fields` returns each link's `type` alone - no `linkFieldValues` - so `entity_get_links` always asks for `id`; any entity field name is accepted, a name the linked type lacks comes back null, an unknown one answers 422, and the linked entity's type is not reported (`entityType` is not a field). `DELETE .../links?right=<id or shortId>` answers 200 `null`, works from either end, and answers 422 "Связь не существует." for a pair that is not linked. `links` on `PATCH v3/entities/...` are applied only when a field changes to a *new* value (or a `comment` comes along): re-sending the current `summary` answers 200 and silently drops them.
- **Entity attachments** (verified 2026-10-26): files reach a project, portfolio or goal through a comment - `POST .../comments` with `attachmentIds` of a temporary attachment - and the listing (`GET v3/entities/{type}/{id}/attachments`) names that comment in `commentId`; `mimetype` is lower case there. `GET .../attachments/{id}` (undocumented) answers the one file, 404 "Вложение не существует." for an id of another entity; `DELETE .../attachments/{id}` (undocumented) answers 204 and leaves the comment, a second time 404 "Вложений N не существуют.", passed through as Tracker's text.
- **Goal key results** (`keyResultItems`, verified 2026-10-26 on a temporary goal): there is no per-item endpoint (`.../keyResultItems[/{id}[/_move]]` answer 404) - every write is `PATCH v3/entities/goal/{id}` with `fields.keyResultItems` set to `{"add": item}`, `{"remove": {"id": ...}}`, a whole list, or `null` (all gone). A list replaces them all and **gives every item a new id**; an `id` inside it answers 422 "Поля [id] только для чтения.", so `goal_update_key_result` / `goal_move_key_result` read the list, convert each item to the write shape (`_key_result_draft`: assignee by id, deadline as a date, status by key) and send it all back. `remove` by `{id}` alone works and keeps the other ids, but an unknown id is a 200 no-op and the item as read answers 400 (its `status` is an object) - hence the read and `EntityItemNotFound`. Items carry `status` (`{id, display}`, undocumented), writable with any goal status key; a `binary` item written without one gets it derived from `achieved`, so the update drops the old status when only `achieved` changes. `type: value` without `progress` answers 422 "Требуется параметр progress.".
- **Entity metrics** (`metricItems` of a project, portfolio or goal, verified 2026-10-27 on temporary ones): written like key results - `{"add": {text, url?}}`, a whole list (every metric gets a new id) or `null` - but **`remove` needs the metric whole** (`{id, text, url}`, `url` may be null): `{id}` alone answers 200 and removes nothing, as does an unknown id, so `entity_delete_metric` reads the list first. `url` is optional and checked (`"not a url"` answers 422 "URI ... неверный"). `entity_update_metric` rewrites the list.
- **Entity permissions** (verified 2026-10-27 on temporary projects): `GET v3/entities/{type}/{id}/extendedPermissions` answers `acl` (`READ` / `WRITE` / `GRANT`, each with `users`, `groups`, `roles`), `permissionSources` (the parent the rights are inherited from, absent when they are the entity's own), `parentEntities` and the undocumented `accessType` (`public` while the group "Все сотрудники" holds WRITE, else `custom`); `.../permissions` is the `acl` part alone and is not used. A right includes the lower ones: granting WRITE drops the subject from READ, revoking READ revokes WRITE too, and a public entity has no `READ` key at all. Setting a parent turns inheriting on. **While inheriting, a change to `acl` answers 200 and is silently dropped** - through either endpoint - so `entity_update_permissions` reads first and raises `EntityPermissionsInherited`; `permissionSources: []` together with the change in one `PATCH` works and is what `inherit=false` sends; `permissionSources: [<primary parent id>]` (`inherit=true`) restores it, and a non-direct parent answers 422 "Наследовать права можно только от прямых родителей". Values may be single (`"roles": "MEMBER"`) or lists; an unknown login answers 422, an unknown role 400, an empty body 200. `*_update_permissions` asks the user to confirm by elicitation, like `queue_update_permissions`.
- **Worklog search** (`POST v3/worklog/_search`) filters only by `createdBy` and by `createdAt` - when a record was *entered*, not the `start` of the work it records - and the documentation says nothing of paging, so the client follows a `Link: rel="next"` if one comes back (guarded by `_MAX_WORKLOG_SEARCH_PAGES`). `worklogs_find` turns `start_from` into the entry window `createdAt >= start_from` and checks `start` itself, which misses only time logged in advance; days are the server's local days (`local_day_start` / `local_day_end` in `mcp/utils.py`). Results from queues outside `TRACKER_LIMIT_QUEUES` are dropped by the issue key.
- **Absences** (`POST v3/gaps/_search`, since 07.2026) need organization-administrator rights - a 403 becomes `AbsencesForbidden` - take at most 100 users and page by user; the user object of each row is cut down to `login` / `display` (`AbsenceUser`). Writes (verified on the live API 2026-10-26): `POST v3/gaps` with `{"gaps": [...]}` answers 200 with the saved rows and full user objects (`user` by login works, an unknown one answers 422 "пользователи [...] не существуют", an unknown `workflow` or `to` not after `from` 422 with a readable text); an `id` that already exists answers **500** "Внутренняя ошибка" instead of updating the absence, so the create tool sends no `id` and an absence is changed by deleting and creating it. `DELETE v3/gaps?gapIds=a,b` answers 204, also for unknown or already deleted ids; without `gapIds` 400. `GET v3/gaps/workflows` lists the ten kinds (`AbsenceKind`). The write tools (`user_write.py`) are not covered by the queue restrictions - an absence belongs to no queue.
- **Reports** (`v3/entities/report`, verified on the live API 2026-10-26): an issue export ('Выгрузка задач', `type: issueFilterExport`, `format` xlsx / csv / xml; an unknown format answers 400 "Unrecognized value") or a worklog report (`worklogReport`, made in the UI). `POST v3/entities/report/` (trailing slash) answers 200 with `id` / `shortId` and no `fields`; Tracker builds the file within a second (`entityStatus: done`). **The API offers no way to get the file**: `.../attachments` is empty, `expand=attachments` answers 422, `.../download` and the like 404, and no field holds it - the tools say so. `GET .../{id or shortId}?fields=summary,entityStatus,parameters` nests them under `fields` (`Report` lifts them); an unknown id answers 404 "сущность [...] не существуют", a malformed one 400. `POST .../_search` takes `fields=summary,entityStatus` but answers **500** to `parameters`; its totals are in the body (`hits`, `pages`); `filter.author` takes a **uid only** - a login answers `hits: 0` - so `reports_find` resolves a login through `user_get`. `DELETE .../{id}` answers 204, then 404. Reads are not cached.
- **Dashboards** (verified on the live API 2026-10-27 on dashboards created and deleted for it): documented are only `POST v3/dashboards` (201; `owner` as a login string or `{"id": login}` both work; an unknown `layout` answers 400 "Unrecognized value") and `POST v3/dashboards/{id}/widgets/cycleTime` (201; `description` required - 422 "Требуется параметр."; statuses go as `[{"key"}]`, an unknown one answers 422 "статусы [...] не существуют"; `bucket.unit` comes back as `bucket.type`). Undocumented but working: `GET v3/dashboards/{id}` (widgets as `{id, display}` references), `DELETE v3/dashboards/{id}` (204, the widgets go with it - `GET v3/widgets/{id}` then answers 404 "Виджет не существует."), `POST v3/dashboards/_search` (the whole list; `page` is ignored and `perPage` is capped at 500, so one request at 500 is the listing, totals in `X-Total-Count`; a `filter` answers 400) and `GET v3/widgets/{id}` (not used). `GET v3/dashboards` answers 405, `DELETE v3/widgets/{id}` 405 - a widget cannot be removed on its own. 404 on a dashboard path → `DashboardNotFound`. Reads are not cached.
- **Templates** (verified on the live API 2026-10-27 on the temporary queue MCPTMW): the reference documents none of `v3/issueTemplates` / `v3/commentTemplates`, but both take `POST` (201; `name`, an optional `queue` - without one the template is the user's own, offered in every queue), `PATCH .../{id}?version=N` and `DELETE .../{id}?version=N` (204, then 404 "Шаблон тикета не существует."). `version` is required on both (**428** without it), a stale one answers **412** "Шаблон тикета: не удалось сохранить изменения" → `TemplateVersionConflict`; the write tools read the template for it when the caller gives none, so the single template reads are not cached. An empty `PATCH` answers 200 without a change (`TemplateEmptyUpdate`). **`fieldTemplates` in a `PATCH` replaces the whole map**, as `checklistItems` does. `fieldTemplates` takes references by key, id or login and answers them as whole objects (`{self, id, key, display}`); `deadline` in it answers 400 "Некорректный формат данных"; an issue template also carries `checklistItems` (with `assignee` as a full user) and `metricItems`. `POST v3/queues/{q}/issueTemplates` answers 405 - the queue goes in the body. `POST /v3/issues` has no `templateId`, so `issue_create` expands the template itself: its `fieldTemplates` values, references cut to `{id}` (`_template_value`), go in the `fields` body under every argument the caller passed and under the caller's own `fields`; `summary` may come from the template alone; its checklist is added by `issue_add_checklist_items` right after the create (a create body takes no checklist). A template bound to another queue is refused.

## Testing

### Rules

- Use **pytest** with asyncio mode `auto`
- Use **aioresponses** for HTTP mocking in `TrackerClient` tests and `@tests/aioresponses_utils.py` for capturing request/response pairs.
- Use **AsyncMock** with `spec=` for protocol mocking in MCP tool tests
- Always type-hint all parameters including fixtures
- Never import inside functions - all imports at top of file
- Never use loops for test cases - use `@pytest.mark.parametrize`
- Use `model_construct()` for creating Pydantic model fixtures (skips validation)

### Test Locations

| What to test               | Where                                      |
|----------------------------|--------------------------------------------|
| TrackerClient HTTP methods | `tests/tracker/custom/test_*.py`           |
| Caching wrappers           | `tests/tracker/caching/test_*_protocol.py` |
| MCP tools                  | `tests/mcp/tools/test_*_tools.py`          |
| OAuth provider             | `tests/mcp/oauth/`                         |

### Testing TrackerClient (HTTP layer)

Use `aioresponses` to mock HTTP requests. Verify request headers and response parsing:

```python
async def test_api_method(self, client: TrackerClient) -> None:
    with aioresponses() as m:
        m.get("https://api.tracker.yandex.net/v3/endpoint", payload={"key": "value"})
        result = await client.api_method()
        assert result.key == "value"
```

### Testing MCP Tools

MCP tools are tested via `mcp.Client.call_tool()` against a real `MCPServer` with mocked protocols.

Key fixtures (from `tests/mcp/conftest.py`):
- `client_session`: Connected MCP client session
- `client_session_with_limits`: Session with queue restrictions enabled
- `mock_issues_protocol`, `mock_queues_protocol`, etc.: Mocked protocol instances

Use `get_tool_result_content(result)` helper to extract tool return values.

```python
async def test_tool(self, client_session: Client, mock_issues_protocol: AsyncMock) -> None:
    mock_issues_protocol.issue_get.return_value = sample_issue
    result = await client_session.call_tool("issue_get", {"issue_id": "TEST-1"})
    assert not result.is_error
    content = get_tool_result_content(result)
    assert content["key"] == "TEST-1"
```

For paginated methods, use `side_effect` for sequential returns: `mock.method.side_effect = [page1, []]`

## Adding New MCP Tools

### Implementation Checklist

1. **Protocol**: Add method signature to the matching `mcp_tracker/tracker/proto/*.py` (a new protocol also needs a `*ProtocolWrap` base, a `CacheCollection` slot, an `AppContext` field and wiring in `make_tracker_lifespan`)
2. **Client**: Implement in `mcp_tracker/tracker/custom/client.py`, through `self._request()` / `self._read()` - see *Talking to the Tracker API* above (this holds for read-only methods too)
3. **Caching**: Add wrapper in `mcp_tracker/tracker/caching/client.py`
4. **Tool**: Add function to appropriate module in `mcp_tracker/mcp/tools/` - named and described per [`rules/tool-naming.md`](rules/tool-naming.md) and [`rules/tool-descriptions.md`](rules/tool-descriptions.md):
   - Queue read-only tools → `queue.py`
   - Queue write tools → `queue_write.py`
   - Global field/metadata tools → `field.py`
   - Issue/comment template tools → `template.py`; write tools → `template_write.py`
   - Board/sprint tools → `board.py`
   - Component read-only tools → `component.py`; write tools → `component_write.py`
   - Issue read-only tools → `issue_read.py`
   - Issue write tools → `issue_write.py`
   - Temporary attachment tools → `attachment_write.py`

**Write tools** (`*_write.py`) are only registered when `settings.tracker_read_only=False`.

**Entity tools** (project/portfolio/goal, read and write alike) are only registered when `settings.tracker_entities_enabled=True`.

**Workflow write tools** (`workflow_write.py`, and `catalog_write.py` and `field_write.py` with them) additionally need `settings.tracker_workflows_write_enabled=True`; they are listed in `WORKFLOW_WRITE_TOOL_NAMES` in `test_server_creation.py`.

## Configuration

Authentication (one required):
- `TRACKER_TOKEN`: Static OAuth token
- `TRACKER_IAM_TOKEN`: Static IAM token
- `TRACKER_SA_*`: Service account credentials for dynamic IAM tokens

Organization (one required):
- `TRACKER_CLOUD_ORG_ID`: For Yandex Cloud
- `TRACKER_ORG_ID`: For on-premise

Optional:
- `TRACKER_LIMIT_QUEUES`: Restrict access to specific queues (allow-list, reads and writes).
- `TRACKER_READ_ONLY`: When `true`, disables all write tools (the `*_write.py` modules)
- `TRACKER_READ_ONLY_QUEUES`: Per-queue read-only allow-list. Write tools stay registered, but mutating calls targeting a listed queue are rejected via `check_*_access(..., write=True)` in `_access.py`; reads still work.
- `TRACKER_ENTITIES_ENABLED`: When `true`, registers the project/portfolio/goal tools (`project*.py`, `portfolio*.py`, `goal*.py`). Default `false`: they add a large tool manifest and are not covered by the queue restrictions above, since an entity isn't mappable to a single queue.
- `TRACKER_FILE_UPLOAD_ENABLED`: When `true` (and not read-only), registers `issue_add_attachment`, which reads a file from the server's filesystem by a caller-given path. Default `false`. `Settings` refuses it unless `TRANSPORT=stdio` and `OAUTH_ENABLED=false`: on a networked server a client, or a prompt injected into issue text, could upload `.env`, `~/.ssh/*` or `/proc/self/environ` to an issue.
- `TRACKER_API_TIMEOUT`: Per-request budget in seconds (default `10`), covering the whole request including the body.
- `TRACKER_AI_ACCESS_IGNORED_QUEUES`: Comma-separated queue keys whose 'AI tools access' setting is ignored (see *AI tools access* above).
- `TRACKER_BULK_ENABLED`: When `true` (and not read-only), registers the bulk-change tools; listed in `BULK_TOOL_NAMES`. Default `false`.
- `TRACKER_ADMIN_ENABLED`: When `true`, registers the administration tools (see *Administration* under Architecture). Default `false`: they are a third of the tool manifest and an agent working issues does not need them.
- `TRACKER_WORKFLOWS_WRITE_ENABLED`: When `true` (and not read-only), registers the workflow write tools (`workflow_write.py`) and the status, resolution, issue type and priority write tools (`catalog_write.py`); listed in `WORKFLOW_WRITE_TOOL_NAMES`. Default `false`: a workflow is often shared by many queues (the `*PresetWorkflow` ones by every queue running them) and a change applies to all of them, and every write re-creates the transition screens it sends, which the API cannot delete.
- `TRACKER_ATTACHMENT_DOWNLOAD_ENABLED`: When `true`, registers `issue_download_attachment` (read-only mode included), which saves attachments to the server's disk. Default `false`, and refused off stdio / with OAuth like the upload flag.
- `TRACKER_ATTACHMENTS_DIR`: Where downloads are saved (default `<system temp>/yandex-tracker-mcp/attachments`, one folder per issue).
- `TRACKER_MAX_ATTACHMENT_BYTES`: Largest attachment `issue_download_attachment` fetches (default 50 MiB).
- `TRACKER_ATTACHMENT_TIMEOUT`: Budget in seconds for one attachment upload or download (default `300`), passed per request through `_request(timeout=..., timeout_setting=...)` so a timeout names this variable rather than `TRACKER_API_TIMEOUT`.
- `TOOLS_CACHE_ENABLED`: Enable Redis caching
- `OAUTH_ENABLED`: Enable OAuth provider mode
